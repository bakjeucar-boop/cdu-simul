# AI 데이터센터 CDU 디지털 트윈 — 소개자료 구성방안

> **대상**: 사내 경영층
> **형식**: HTML 단일 파일 (시연 화면 `demo/pfd.html` 로 자연스럽게 이어지도록)
> **이 문서의 성격**: 구성 설계안이다. 실제 문구·수치는 HTML 제작 시 정본 문서에서 다시 확인해 넣는다.
> **모든 페이지 공통**: 「가정값 기반 — 실측 아님」 표기 (CLAUDE.md 절대 규칙 11)

## 0. 이 자료가 하는 일 / 하지 않는 일

### 하는 일
- 이 접근이 **말이 되는 구조**임을 보인다
- 그 판단의 **근거가 공학 계산**임을 보인다
- 다음 단계에 무엇이 필요한지를 **비용과 함께** 제시한다

### 하지 않는 일 (사람 승인 완료)
| 쓰지 않을 것 | 이유 |
|---|---|
| **「누출 조기감지가 된다」** | 현 K값 근사의 신호 방향이 실제 질량손실 누출과 정반대 (판정 5-b = X). **기능 확보 전까지 일절 언급하지 않는다** |
| 「예측이 정확하다」 | 실측이 없어 정확도를 잰 적이 없다. 「무너지지 않는다」까지다 |
| 출처 없는 수치 | 5장 가정치는 전부 출처 표기 |
| 「Aspen 을 대체한다」 | 「용도가 다르다」로 쓴다 (§6 참조) |

> **누출 관련 어휘 통제**: 화면과 마찬가지로 자료 전체에서 「누출」을 쓰지 않는다.
> 시나리오 축 이름은 **「랙 배관 저항 증가」** 로 통일한다.
> 「이상 상태」·「비정상 운전」 정도로 표현한다.

## 1. 전체 구성 — 6장

> **순서를 바꿨다.** 요청하신 「개요 → 과정 → 기대효과 → 시연 → 개선방향 → 개선후 기대효과」에서
> **시연을 앞으로 당겼다.** 경영층은 공학 설명을 먼저 만나면 페이지를 넘긴다.
> 「이게 우리가 만든 것입니다」를 먼저 보이고 그 다음에 「이 숫자가 어떻게 나왔는지」로
> 들어가면, 공학 내용이 결론이 아니라 **근거**로 읽힌다.

| # | 장 | 분량 | 이 장이 답하는 질문 |
|---|---|---|---|
| 1 | 왜 만들었나 | 1 화면 | 무슨 문제가 있나 |
| 2 | 무엇을 만들었나 — 시연 | 1 화면 + 실물 | 결과물이 뭔가 |
| 3 | 이 숫자는 어떻게 나왔나 | 3~4 화면 | 근거가 뭔가 (**자료의 핵심**) |
| 4 | 지금 할 수 있는 것 | 1~2 화면 | 당장 무슨 쓸모가 있나 |
| 5 | 무엇이 더 필요한가 | 1 화면 | 한계가 뭔가 |
| 6 | 그 다음에 할 수 있는 것 | 1~2 화면 | 투자하면 뭘 얻나 |

## 2. 1장 — 왜 만들었나

### 담을 것
- D2C 액체냉각이 AI/GPU 고집적화로 불가피해지고 있다
- **밀폐 소형 배관은 이상을 즉시 확인하기 어렵다** — 이것이 과제의 문제의식
- 실제 설비로는 이상 조건을 만들어 볼 수 없다. **시뮬레이션이 유일한 길**이다
- 상위 배경: 데이터센터 유기냉매(PG25 등) 적용 초기 단계, 화학물질 위험 사전 인지·완화

### 쓰는 방식
문제 제기 한 화면. 숫자를 많이 넣지 않는다.

### 주의
「누출감지센서는 사고 이후에야 감지한다」까지는 **업계 현황 서술**이라 쓸 수 있다.
그러나 「그래서 우리가 조기감지를 한다」로 이어가지 않는다 —
「그래서 설비 거동을 계산으로 재현할 필요가 있다」로 잇는다.

## 3. 2장 — 무엇을 만들었나 (시연)

### 구성
1. **정지 화면 캡처 1장** — 서버실 탭, dual, 부하 100 %, 저항 0 %
2. **읽는 법 3줄** — 슬래브 높이 = 부하 · 색 = 랙 간 온도 편차 · 왼쪽 = CDU 내부
3. **「직접 열어보기」 버튼** → `demo/pfd.html`

### 시연 시나리오 (발표자용 · 자료에도 짧게)
| 조작 | 보이는 것 | 말할 것 |
|---|---|---|
| 부하 20 → 100 % | 슬래브가 자라고 랙이 붉어진다 | 부하가 온도로 전달되는 경로 |
| 구성 단일 → 2대 | CDU 그림 둘, 2차측 배분이 갈린다 | 공유 2차측을 통한 CDU 간 연동 |
| 저항 0 → 50 % | **랙 08 막대 45 px · 총유량 막대 11 px** | **약 4배 차 — 계측 위치가 결정적이다** |

> **이 자료에서 가장 강한 한 장면은 세 번째다.**
> 두 막대가 같은 축척(77 px per m³/h)인데 길이가 4배 차이 난다.
> 국소 이상이 총량 계측에는 거의 안 잡힌다는 것을 말없이 보여준다.
> **「누출」이라 부르지 않고 「랙 배관 저항 증가」로 부른다.**

### 시연 뒤 한 줄
「이 화면의 모든 숫자는 임의로 넣은 것이 아니라 물리 계산의 결과다」
→ 3장으로 넘어가는 다리

## 4. 3장 — 이 숫자는 어떻게 나왔나 (**핵심**)

### 쓰는 방식 — 「화면의 이 숫자」 → 「이 식」
장치별로 **화면에 보이는 특정 숫자를 짚고** 그것이 어느 공학 원리에서
나왔는지 보인다. 식을 나열하지 않는다.

### 3-1. 장치별 공학 내용

| 장치 | 화면의 숫자 | 쓰인 공학 | 한 줄 설명 |
|---|---|---|---|
| **펌프** | 총유량 55.83 m³/h | 특성곡선 `H = H₀ − aQ − bQ²` · 시스템곡선과의 교점 | 펌프가 낼 수 있는 압력과 계통이 요구하는 압력이 같아지는 자리를 푼 값 |
| **밸브** | (내부 계산) | `Kv = Q√(SG/ΔP)` 역산 | 기기 특성은 고정, 온도가 바뀌면 ΔP 가 움직인다 |
| **배관** | 랙별 유량 6.71~7.27 m³/h | `ΔP = K·ρv²/2` · 병렬 분배 `Q ∝ 1/√K` | 헤더 압력이 8개 다리에서 같아야 한다는 연립방정식의 해 |
| **열교환기** | 640 kW · 공급 32.169 ℃ | ε-NTU 법 (대향류) `Q = ε·C_min·ΔT_max` | 2차측 27 ℃ 로 1차측을 어디까지 식힐 수 있는지 |
| **랙** | 출구온도 42.058~42.883 ℃ | `Q = ṁ·cp·ΔT` · CoolProp 실물성 | 부하는 같은데 유량이 달라 온도차가 벌어진다 |

### 3-2. 강조할 셋 — 이 자료의 무게중심

#### ① 물성이 상수가 아니다
PG25(25 wt% 프로필렌글리콜 수용액)의 비열·밀도를 **CoolProp 에서 그때 온도로 조회**한다.
물로 계산하면 답이 달라진다.

#### ② 압력과 온도를 다른 방식으로 푼다 (하이브리드)
- 압력-유량 → 매 시점 대수방정식 (`fsolve`)
- 온도 → 열용량 기반 시간적분 (`solve_ivp`)

**이유: 관성 시간상수가 다르다.** 압력은 거의 즉시 평형에 가고 온도는 분 단위로 움직인다.
둘 다 정상상태로 단순화하면 과도 거동이 사라지고, 둘 다 시간적분하면 계산이 무거워진다.

> **이 대목을 반드시 넣는다.** 「단순 계산이 아니다」가 가장 확실히 전달되는 자리다.

#### ③ 역방향 검증 — 표가 맞는지를 계산이 확인했다
5장 표는 1차측 32/42 ℃ 를 준다.
대향류 · NTU 2 · 2차측 27 ℃ 로 계산하니 **32.17 / 42.47 ℃** 가 나왔다.
→ **표가 대향류를 상정해 만들어졌음이 계산으로 확인됐다.**
가정을 새로 만든 것이 아니라 표에서 역으로 읽어낸 것이다.

### 3-3. 「이게 맞는지 어떻게 아는가」 — 검증

| 검증 항목 | 결과 |
|---|---|
| 에너지 balance 오차 | **0.00506 %** (기준 0.1 %) |
| 부하 증가 시 환수온도 방향 | 16조합 전부 성립 |
| 극단 케이스(부하 0 / 100 %) | 발산 없음 |
| 자동 시험 | 1,207건 전부 통과 |

#### 딸린 사실 하나 — 설득력을 크게 올린다
**물성 평가 온도를 어디로 잡느냐로 판정이 갈렸다.**

| 평가 기준 | balance 오차 | 판정 |
|---|---|---|
| 벌크 평균온도 | 0.005 % | **통과** |
| 공급온도 | 0.309 % | 실패 |
| 환수온도 | 0.315 % | 실패 |

→ 검증이 형식적이지 않다는 증거다. 규칙 하나로 결과가 뒤집힌다.

### 3-4. 규모 — 설비로는 못 하는 일

- **136 케이스** (CDU 구성 2 × 부하 17단계 × 저항 4단계) 를 배치 실행
- 실제 CDU 로 랙 배관 저항을 50 % 올려볼 수는 없다
- 결과가 바로 데이터 표로 나온다

## 5. 4장 — 지금 할 수 있는 것

> **원칙: 「설득·검토·설계의 도구」까지다. 운영 판단의 근거가 아니다.**

### ⑴ 구조가 성립함을 보인다
구성요소가 각각 독립 모델로 서고, 물렸을 때 전체 거동이 나온다. (판정 1 = O)

### ⑵ 계측 설계를 사전 검토한다 — **가장 강한 활용처**

> 「AI 로 예측한다」는 누구나 말한다.
> **「어디에 계기를 달아야 하는지를 짓기 전에 안다」**는 구체적이고 비용이 눈에 보인다.

- **압력 계열 신호는 매우 작다** — 랙 배관 저항이 늘 때 양정 변화가 양정 대비 상대 5e-5 수준.
  압력계로 미세 변화를 잡겠다는 계획이 있다면 그 정밀도를 낼 계기가 있는지부터 확인해야 한다
- **총량 계측의 한계** — 저항 +50 % 에서도 총유량 변화는 −0.16~0.37 %.
  국소 이상을 총량으로 잡기 어렵다 (2장 시연의 4배 차와 같은 이야기)
- **공급−환수 차가 배치에 강인하다** — 유량계를 어디에 다느냐를 고를 때의 근거

### ⑶ 설계 조건의 감도를 본다
- **잔여저항(HX 1차측 + CDU 내부배관 + 헤더)이 총양정의 60~83 %** 를 차지한다
  → 배관·밸브보다 CDU 내부와 헤더가 유량분배를 지배한다. 무엇을 먼저 확정해야 하는지를 가리킨다
- **25A 랙 분기에 1.94 L/s 면 유속 3.48 m/s** — 냉각수 통상 설계유속 2~3 m/s 보다 높다
  → 실제 설계에서 분기 구경이 커질 가능성이 있고, 그러면 저항과 열용량이 함께 이동한다

### ⑷ 시나리오를 반복 생성한다
정상 320행 · 이상 960행의 정상상태 데이터셋.
**용도: 시연 · 구조 검증.** (학습 데이터로는 아직 쓰지 않는다 — 5장에서 설명)

## 6. 5장 — 무엇이 더 필요한가

> **이 장이 자료의 신뢰를 만든다.** 사내 경영층 대상이므로 한계를 솔직히 적는다.
> 「그래서 안 된다」가 아니라 **「그래서 다음에 이것을 한다」**로 쓴다.

### 6-1. 세 가지 한계

| # | 한계 | 무엇이 필요한가 |
|---|---|---|
| ① | **이상 상태 정의를 다시 세워야 한다** | 현재는 배관 저항 변화로 근사했다. 질량이 보존되는 모사라 실제 물리와 다르다. 정의 교체가 필요하다 |
| ② | **시간축을 다시 세워야 한다** | 배관 이산화 방식에 따라 과도 파형이 달라지고, 노드 수 64까지 올려도 수렴하지 않았다. 정상상태 값과 신호 방향은 강인하다 |
| ③ | **설계데이터가 없다** | 5장 전체가 업계 공개자료 기반 가정치다. 정확도는 실측 없이 잴 수 없다 |

> ①을 쓸 때 **「누출」이라는 말을 쓰지 않는다.**
> 「이상 상태 정의」·「시나리오 정의」로 표현한다.

### 6-2. 열용량이 실제보다 작다
열교환기·CDU 내부·랙 콜드플레이트 보유량이 가정치 표에 없어 빠져 있다.
→ 모델의 수렴시간이 실제보다 짧게 나온다. **설계도서에서 채울 수 있다.**

### 6-3. CDU 간 연동이 절반만 들어 있다
2차측 공급온도를 고정 경계조건으로 두었다.
→ CDU 간 연동이 **유량 경로로만** 생기고 열 경로로는 생기지 않는다.
냉각탑·드라이쿨러 모델을 넣으면 닫힌다.

## 7. 6장 — 그 다음에 할 수 있는 것

### 3단계로 나눠 제시 — 각 단계에 **무엇이 필요하고 무엇을 얻는지**

#### 1단계 — 정의 교체 + 시간축 재수립
**필요**: 추가 개발 (설계데이터 불필요)
**얻는 것**:
- 이상 상태의 물리적 방향이 실제와 맞는 시나리오 데이터
- 「언제부터 이상했는가」를 다룰 수 있는 시간축
- 판별 규칙의 오경보율·검출 지연을 시뮬레이션으로 먼저 재보기

#### 2단계 — 설계데이터 투입
**필요**: 실제 펌프·밸브·HX 사양, 랙별 발열량
**얻는 것 — 설계 단계 활용**:
- 펌프 용량 선정 — 「이 곡선이면 최대 부하에서 운전점이 어디인가」
- 헤더 구경 결정 — 「80A 면 랙 간 유량 편차가 얼마인가」
- 여유율 검토 — 「640 kW 부하에 750 kW 정격이 적절한가」
- 랙 증설 영향 — 「8개를 12개로 늘리면 가장 먼 랙 유량이 얼마나 주는가」를 시공 전에

#### 3단계 — 시운전 · 운영
**필요**: 실측 데이터, 동적 해석 보완 (§8)
**얻는 것**:
- **밸런싱** — 랙 간 유량을 맞추는 밸브 개도를 현장 시행착오 대신 모델이 먼저 낸다
- **못 돌려본 조건 채우기** — 전 랙 100 % 동시, 부하 급변 등 실제로 시험하기 위험한 조건
- **가상 계측** — 센서를 못 다는 자리의 값을 모델이 추정
- **모델 편차 감시** — 절대 임계치가 아니라 「모델이 말하는 값과 실측의 차」로 본다.
  부하가 변해도 오경보가 적다

> **3단계 서술에서도 「누출 조기감지」를 쓰지 않는다.**

## 10. HTML 제작 시 지침

### 시연 화면과의 연결
- 소개자료는 **단일 HTML**, 시연 화면은 별도 파일 (`demo/pfd.html`)
- 2장 끝에서 **버튼 또는 링크로 전환**. 시연 화면에서 돌아오는 길도 둔다
- 두 화면의 **조형을 통일한다** — 시연 화면의 색 여섯 · 선 굵기 · 시스템 폰트를 그대로 쓴다.
  다른 디자인이면 「같은 프로젝트의 산출물」로 안 읽힌다

### 색 (시연 화면과 동일)
```
지면 #EDF0F2 · 장비 면 #FFFFFF · 구조선 #3E4C56
찬 쪽 #2E7FA8 · 뜨거운 쪽 #C2452D · 이상 표시 #E8A33D
```

### 화면 구조
- 세로 스크롤 1페이지 · 장 구분은 앵커
- 기준 1600×900, 노트북 화면에서 확인
- 외부 라이브러리 없이 단일 파일

### 글자 원칙 (시연 화면과 같은 기준)
- 설명 문구 최소화. **도형과 숫자가 말하게 한다**
- 읽는 법을 글로 설명해야 하는 표시는 실패다

### 넣을 그림
| 장 | 그림 |
|---|---|
| 1장 | 없음 또는 계통 개념도 하나 |
| 2장 | 시연 화면 캡처 1장 |
| 3장 | **장치별 공학 내용 다이어그램** — 시연 화면의 CDU 그림을 재활용해 각 장치에 식을 붙인다 |
| 3장 | balance 검증 표 · cp 평가 기준별 판정 표 |
| 4장 | 편차 막대 4배 차 그림 (2장 것 재활용) |
| 6장 | 3단계 로드맵 |

### 반드시 넣을 것
- **모든 화면 하단에 「가정값 기반 — 실측 아님」**
- 5장 수치를 쓸 때 출처 표기

## 11. 제작 전에 정할 것

| # | 정할 것 | 선택지 |
|---|---|---|
| 1 | **분량** | 압축형(6~8 화면) / 상세형(12~15 화면) |
| 2 | **3장 깊이** | 식을 실제로 보일 것인가, 이름만 부를 것인가 |
| 3 | **다음 단계 요청** | 자료 끝에 「무엇을 승인해 달라」를 넣을 것인가 (설계데이터 확보 · 추가 개발 기간 등) |
| 4 | **시연 전환 방식** | 새 탭 / 같은 탭 / 소개자료 안에 iframe 으로 품기 |
| 5 | **발표용인가 배포용인가** | 발표용이면 글자를 더 줄이고, 배포용이면 설명을 더 붙인다 |

> 3번이 가장 중요하다. **이 자료가 무엇을 얻으려는 것인지**가 정해져야
> 6장의 무게가 정해진다. 「알리는 자료」와 「승인을 받는 자료」는 구성이 다르다.
